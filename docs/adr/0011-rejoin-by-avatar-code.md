# Rejoin by Avatar Code: the dispatcher decides, and Current Life includes prison

A player returns to their Avatar — or hands it to someone else — by typing **`XXXX-YY`**: the session's 4-digit `shortId` plus an `avatarIdx`. A single **Code Dispatcher** decides the destination rather than the lookup deciding it by refusing to answer, and the two code forms deliberately resolve over **different session-status scopes**: a bare `XXXX` only against `OPEN` sessions (it means "I am new here", so it leads to avatar creation), an `XXXX-YY` against every session except `ENDED` (it means "put me back", which must keep working long after the session started). The suffixed code lands on the Avatar's **existing player lobby**, which offers a cancellable **Rejoin Countdown** into the running game. Along the way `getCurrentPlayerStateIdx` widens from `status === ALIVE` to "the Life that is not `DEAD`" — the new **Current Life** concept — which fixes a pre-existing bug unrelated to this feature.

## Why the lobby, and not a resolution straight to the board

The player lobby (`/avatar/:sessionId/:avatarIdx`) already answers both hard questions: *which* of the session's two games is joinable, and *which* Life to enter. It gets the first from `AvatarService.getByIdx` → `SessionService.getById(id, true)`, whose `populateStatusForGameRules` reads the live status off the `GameState` document, and the second from `getCurrentPlayerStateIdx`.

That populate is not optional. The `gameStatus` **persisted on the rules subdocument is never updated**: it is born `NONE` in `rules.service.js` and its only writer is `killGame`, which sets it back to `NONE`. So `getByShortId` — a plain `findOne` — reports `gameStatus: 'none'` for every rule, always. A dispatcher that tried to decide "is a game running?" from the short-id lookup would conclude "no" every single time and never forward. Hence the split: **the dispatcher only resolves the trichotomy** (which needs `avatars`, already present in the raw document), and **the lobby owns the forward**, because only the lobby holds trustworthy data.

## Prison was already locking players out

`bank.state.service.js` sets `status = PRISON` and only restores `ALIVE` on release, while `getCurrentPlayerStateIdx` filtered on `status === ALIVE` strictly — so **an imprisoned player resolved to `-1`**.

This is an **alignment, not a new semantic**: `_reincarnate` in the same file already selected the life to end with `p.status !== PLAYER_STATUS.DEAD`, precisely so a scheduled death can land on an imprisoned life (its next line then cancels the prison timer). Current Life was therefore already the de-facto rule for "the Avatar's live life"; `getCurrentPlayerStateIdx` was simply the one place that disagreed with it. Both now read the same test. `lobby-player`'s `joinGame()` never guarded that value and navigated to `/player/.../-1`, where `getPlayerState` 404s. With Auto Seizure (ADR-0005) prison is routine, not a corner case, so this was hitting real players today, without any short code involved. Widening the resolution to "not `DEAD`" sends an imprisoned player back to their board where the prison overlay and its restored countdown belong. `-1` now means only one thing — terminal death, no Current Life at all — and every caller must still guard it.

## Considered options

- **Roster pick** (type `1234`, then tap your own face from the avatar list). Rejected: it cannot serve the handover half of the feature — a substitute player has no face to recognise — and the animator cannot dictate it over the room. An addressable code can be spoken, written on a board, or turned into a QR.
- **Resolve the code straight to the player board.** Rejected: it needs a brand-new "which game is active" rule plus a fallback path to the lobby anyway, so it maintains two routes where the lobby already handles every phase (not started / running / stopped / between the two games) correctly.
- **Auto-forward on every lobby visit** rather than only on code arrival. Rejected: it makes avatar settings and the survey unreachable while a game runs, breaking existing paths.
- **Silent instant forward** on code arrival. Rejected in favour of the countdown: the player sees their own avatar and the game they are about to enter *before* it happens, which is worth one beat when they have just hand-typed a code — and cancelling is what keeps the lobby's other functions reachable.
- **Keep `ALIVE` strict and merely guard `-1`** with a "you cannot enter now" message. Rejected: prison lasts up to `rules.timerPrison` minutes, so it would lock a player out of their own board for the duration.
- **Resolve the current Life by highest `idx`** instead of by status. Rejected: it still needs a status test behind it to refuse a terminal death, so it buys nothing over "not `DEAD`".
- **`.sort({ createdAt: -1 })` on the short-id lookup**, or **redrawing `numbersId4()` until unused**, to contain collisions. Both rejected in favour of the real fix — sessions eventually reaching `ENDED` via an explicit animator close step (deferred, see Consequences). Recency-sorting treats the symptom; unique redraws exhaust a 10 000-value pool that nothing ever releases.
- **Auto-inserting the dash** after the 4th digit, keeping the keypad digits-only. Rejected in favour of adding a real `-` key: what the player reads on the animator's screen is then exactly what they type. This costs a shape validation (`^\d{4}(-\d{1,2})?$`) and makes a backspace key necessary, which the layout currently lacks.

## Consequences

- **The duplicate-avatar bug closes.** Today `/join/1234` unconditionally appends a new avatar (`AvatarService.create` never looks for an existing one), so a player retyping their session code got silently cloned. A bare `XXXX` now refuses once the session has started.
- **`XXXX-YY` naming an absent avatar in an `OPEN` session leads to creation, and the new avatar gets `avatarIndexSeq + 1`, not `YY`.** The typed suffix is discarded, so the screen must say so or the player will believe they are avatar `YY`.
- **Handover costs nothing to build.** The code opens the normal player route, so the same socket identity `s:{sessionId}:a:{avatarIdx}` applies and `socket.js` kicks the incumbent with `KICK_REASON.ANOTHER_CONNECTION`, which already raises a dialog on the displaced device. Two existing warts now sit on a *common* path instead of an accidental one and should be fixed with this work: the dialog concatenates the raw reason token (`another_connection`) onto translated text instead of mapping `KICK_REASON` to i18n keys, and its `disableClose: true` is passed inside `data` rather than the dialog config, so the supposedly blocking dialog is dismissable.
- **Collision safety is borrowed from unbuilt work.** Because nothing currently assigns `ENDED`, "every session except `ENDED`" means every session ever created, and `shortId` is an unchecked 4-digit draw with no unique index. A collision is silent and plausible-looking: the stale session very likely also has an avatar `YY`, so the player lands in a working lobby belonging to a different workshop. This is accepted on the basis that the deferred close-session step (both games finished → close → results) will bound the resolvable pool. If collisions surface first, the interim answer is the recency sort, not a wider code.
- **The Rejoin Countdown is armed only when exactly one game is joinable.** Two simultaneously joinable games — abnormal but reachable — fall back to a plain manual choice.
- **Refusals stay inside the entry dialog** with the typed code preserved, rather than closing it and reporting through `ErrorService`/snackbar as the rest of the app does. A deliberate local deviation: a hand-typed 6-character code on a virtual keypad makes typos the dominant failure, and the existing pattern would force a full re-entry each time. Each cause gets its own message.
